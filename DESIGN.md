# VigorEngine — System Design

Version 1.0 · 2026-09-10 · Status: approved for build

VigorEngine is a local-first AI fitness coach that remembers workouts, nutrition, preferences, constraints and progress, and uses that history to decide what the user should train and eat next. See `idea.md` for the full feature list. This document is the build contract: every package and screen described here is in scope for v1.

---

## 1. Decisions (settled with the owner)

| Question | Decision |
|---|---|
| Platform | Mobile (Expo / React Native) and web (Vite React PWA) sharing one TypeScript core |
| AI access | User supplies their own Anthropic API key. No server. |
| Scope | Full 30-feature set from `idea.md`, built in phases so the app is usable early |
| Audience | Single user now; structured so accounts and sync can be added later without a rewrite |
| Sync | None in v1. Each device is local. Export/import of an encrypted JSON bundle for manual transfer. |
| Food data | AI estimation from natural language, plus saved meals for exact repeats. No external food database. |
| Units | User picks per profile (metric or imperial). Storage is always canonical metric. |
| Stack | pnpm monorepo, TypeScript everywhere, Expo Router for mobile, Vite + React for web |

Toolchain on the dev machine: Node 25.4, pnpm 11.25, git 2.47, no local Android SDK. Mobile runs through Expo Go and EAS development builds; no local native toolchain required.

## 2. Design principles

1. **Engines decide numbers; the model decides selection and explains.** Progressive overload, plateau detection, readiness adjustment, nutrition arithmetic, PR detection and streaks are pure, deterministic functions in `packages/core`. Claude receives their output as facts and reasons on top. This is what makes recommendations explainable, testable, and available offline.
2. **Raw logs are the source of truth. Memories are derived or declared, never the only copy.** Workouts and food logs are tables. Memory records point back at evidence.
3. **Every recommendation carries a `rationale`.** A structured list of reason codes plus a human sentence. The UI always shows "Why?".
4. **Offline is the default state.** Anything that does not need reasoning works without network. AI work that fails offline is queued, not lost.
5. **One core, two shells.** Domain logic, storage, AI orchestration, and view-models live in shared packages. The apps contain only components, navigation, and platform adapters.
6. **Safety interrupts progression.** Pain, injury, dizziness, or unusual symptoms flip a safety state that every engine and prompt respects.

## 4. Data model (`packages/db`)

SQLite on both platforms. Drizzle ORM with the `sqlite-proxy` driver so one repository codebase runs against both drivers through this interface:

```ts
export interface SqlDriver {
  run(sql: string, params: unknown[]): Promise<{ rows: unknown[][]; changes: number }>;
  transaction<T>(fn: (tx: SqlDriver) => Promise<T>): Promise<T>;
}
```

Mobile implements it with `expo-sqlite`. Web implements it with `@sqlite.org/sqlite-wasm` using the `opfs-sahpool` VFS inside a Web Worker (no COOP/COEP headers required, so the PWA can be hosted anywhere static). Migrations are SQL files generated by drizzle-kit and applied by a `migrate(driver)` function on app start.

All IDs are UUID v7 strings. All timestamps are ISO 8601 UTC strings. All dates that mean "a calendar day for the user" are `YYYY-MM-DD` local strings. Canonical units: kg, cm, g, kcal, seconds.

## 5. Domain engines (`packages/core`)

All engines are pure functions: `(inputs) → { result, rationale }`. `Rationale` is:

```ts
interface Rationale {
  codes: string[];          // e.g. ["ALL_SETS_TOP_OF_RANGE", "RPE_UNDER_THRESHOLD"]
  facts: Record<string, unknown>;   // the numbers that drove the decision
  summary: string;          // one plain sentence, template-generated, no AI needed
}
```

### 5.1 Progression engine (double progression)

Input: last 1–3 sessions of an exercise (sets with reps, load, RPE), target rep range, load increment for the equipment used, readiness modifier, safety state.

Rules, evaluated in order:
1. Safety state active → hold load, reduce sets by 1, code `SAFETY_HOLD`.
2. Readiness modifier is `reduce` → hold load, volume −30 %, code `READINESS_REDUCE`.
3. Readiness modifier is `hold` → hold load, code `READINESS_HOLD`.
4. All working sets hit the top of the rep range and mean RPE ≤ 8.5 → increase load by one increment, target reps reset to bottom of range, code `PROGRESS_LOAD`.
5. Bodyweight/time/distance load types → progress by reps (+1–2), time (+10 %) or harder variation via `exercise_relations.progression`, code `PROGRESS_REPS` / `PROGRESS_VARIATION`.
6. Any set below the bottom of the range and mean RPE ≥ 9.5 on two consecutive sessions → decrease load one increment, code `REGRESS_LOAD`.
7. Otherwise hold load and target the next rep milestone, code `HOLD_BUILD_REPS`.

Load increments default per category (barbell 2.5 kg, dumbbell 2 kg, machine 5 kg, kettlebell next bell, band next band) and are overridable per equipment row. In imperial profiles increments are 5 lb / 5 lb / 10 lb and converted to kg for storage; the display layer rounds to what the user can actually load.

### 5.2 Readiness engine

Input: today's readiness row. Score = weighted sum normalised to 0–100 (sleep quality 30 %, energy 25 %, fatigue 20 %, soreness 15 %, stress 10 %; sleep hours under 6 subtracts 10). Output modifier: `normal` (≥ 65), `hold` (45–64), `reduce` (< 45). `painReported` always yields `safety` and creates a `safety_events` row.

### 5.3 Plateau & deload detector

Per exercise: no new e1RM or rep PR over the last 4 sessions and mean RPE trend rising → `PLATEAU` insight with suggestions (variation swap via relations, rep range change, deload).
Global: rolling 14-day RPE mean ≥ 8.8 and weekly volume ≥ 1.3 × the 6-week mean, or two readiness `reduce` days in one week → `DELOAD_RECOMMENDED` (next week volume −40 %, loads −10 %). Deload is proposed, not imposed; the coach explains and the user accepts.

### 5.4 Rule-based planner (offline workout generation)

Chooses a session template from goals and the last 7 days of muscle-group volume: picks the least recently trained major pattern group, respects `preferredDurationMin` (each exercise costs `sets × (restSec + 40 s)`), filters exercises by available equipment, location and dislikes, and applies the progression engine to each. Output is a `WorkoutPlan` with rationale. This is the fallback when the coach is offline and the baseline the coach refines when online.

### 5.5 Substitution engine

`substitute(exerciseId, reason, ctx)` ranks candidates by: same movement pattern (must), primary muscle overlap (weight 3), equipment available (must), difficulty within ±1 (weight 2), explicit `substitution` relation (weight 4), user has history with it (weight 1), not disliked (must). Returns top 3 with rationale.

### 5.6 Nutrition math

Daily state from `food_items` for the date versus the active `nutrition_targets`. Remaining values never go below 0 in the UI but are stored signed. Initial targets when the user has none: Mifflin-St Jeor BMR × activity multiplier, adjusted by primary goal (fat loss −20 %, hypertrophy +10 %, others 0), protein 1.8 g/kg, fat 25 % of kcal, carbs the remainder, fiber 14 g per 1000 kcal. The user can override any value.

### 5.7 PR & streak engine

After every completed set: compute e1RM with Epley (`load × (1 + reps/30)`, only for reps ≤ 12), compare to `personal_records`. Streaks count planned-day completions; a rest day never breaks a streak.

### 5.8 Insight detectors (run on app open, at most once per day)

Each detector returns zero or more insights with evidence. Required set:
- `EXERCISE_TREND` — linear regression on e1RM over ≥ 6 sessions, slope reported per week
- `PUSH_PULL_BALANCE` — 4-week set volume ratio outside 0.75–1.33
- `SKIPPED_PATTERN` — a weekday or duration bucket with completion rate < 50 % over 4 weeks
- `PROTEIN_GAP_BY_DAY` — weekday groups where protein averages < 85 % of target
- `COMPLETION_BY_DURATION` — completion rate by planned duration bucket
- `FREQUENT_FOODS` — items logged ≥ 4 times in 14 days (feeds saved-meal suggestions)
- `MISSED_TARGET_STREAK` — any macro missed 5 of the last 7 days

Detectors are deterministic. Claude is only asked to phrase a batch of insights into the weekly review.

### 5.9 Weekly review builder

Deterministic stats object (completed/planned, volume by muscle group, PRs, missed sessions, average kcal/protein, macro consistency, top insights). Stored first; the coach summary is an `ai_job` that fills `summary` and `recommendation` when online.

### 5.10 Units

`packages/core/units`: `toDisplay(valueMetric, kind, unitSystem)` and `fromInput(value, kind, unitSystem)` for weight, length, load. Rounding rules: display load to the nearest achievable plate increment, body weight to 0.1.

## 6. AI layer (`packages/ai`)

### 6.1 Client

`@anthropic-ai/sdk`. The key is read from the platform SecureStore adapter (expo-secure-store on mobile; on web, IndexedDB with an explicit warning that browser storage is not hardware-backed). The web client sets `dangerouslyAllowBrowser: true` because the app has no server by design; the settings screen explains that the key never leaves the device except to `api.anthropic.com`.

Models (settings, user-changeable):
- `coachModel` default `claude-opus-5` for coach chat, workout generation, weekly review, recipes
- `fastModel` default `claude-haiku-4-5` for food-text parsing and memory extraction

Every request: `thinking: { type: "adaptive" }`, streaming for chat, `output_config.effort` `medium` for chat and `low` for parsing. Handle `stop_reason === "refusal"` by showing the coach's fallback line and never crashing. Use the `fallbacks: "default"` beta on Opus 5 requests as the skill recommends, tell the user in settings that it is on.

### 6.2 Context assembly

Each coach turn builds a `CoachContext` under roughly 6k tokens:

```
[system, cached]   coach persona, safety rules, unit system, explanation style, tool guidance
[system, cached]   exercise library digest (names, patterns, equipment) — changes rarely
[user turn]        <context> profile summary, active goals, active memories (top 30 by recency),
                   last 7 workouts (one line each), today's readiness + modifier, today's nutrition
                   state, safety state, engine outputs already computed for today (planner draft,
                   progression decisions, open insights) </context> + the user's message
```

Stable blocks come first with `cache_control` breakpoints so the prefix caches across turns. Volatile data always sits after the last breakpoint.

### 6.3 Tools (executed locally, defined with `betaZodTool`, run by `client.beta.messages.toolRunner`)

| Tool | Purpose |
|---|---|
| `get_exercise_history({ exerciseId, limit })` | detailed sets for one exercise |
| `search_exercises({ pattern?, muscle?, equipment?, query? })` | library lookup |
| `get_workouts({ from, to })` | history range |
| `propose_workout(WorkoutPlan)` | validated by zod, loads re-checked by the progression engine, stored as `planned`, returned with rationale |
| `substitute_exercise({ workoutExerciseId, reason })` | runs the substitution engine, applies the top pick, returns alternatives |
| `adjust_workout({ workoutId, durationMin?, intensity?, dropExercises? })` | shortens or lightens today's plan |
| `get_nutrition_day({ date })` | consumed / remaining |
| `log_food({ date, mealSlot, items[] })` | writes log + items |
| `get_inventory()` / `update_inventory({ add[], remove[] })` | pantry |
| `save_recipe(Recipe)` / `save_meal(SavedMeal)` | persistence |
| `remember({ kind, domain, text, evidence? })` | creates a `memories` row with `source: coach` |
| `forget({ memoryId })` | soft-deletes |
| `update_profile(partial)` / `update_targets(partial)` | profile edits from chat |
| `report_safety({ kind, text })` | creates a safety event and flips safety state |

The model never writes numbers that the engines own: `propose_workout` inputs are exercise selection, order, set counts and rest; loads and rep targets are filled by the progression engine and the model may only request `hold` or `lighter` overrides with a reason.

### 6.4 Prompt tasks outside chat

- **Food parsing**: `fastModel`, structured output (`output_config.format`) to a `FoodItem[]` schema with confidence. Region hint from `profile.foodRegion` (Indian staples known by default when `IN`). Offline → `ai_jobs` row with `estimate_food`, item shows "estimating…".
- **Recipe generation**: `coachModel`, inputs = inventory, remaining macros, dietary constraints, time, preferences, items with `useBy` in 2 days first. Structured output to `Recipe`.
- **Meal plan**: same, `DayPlan[]`, respects targets per day.
- **Weekly review summary**: `coachModel`, input = the deterministic stats object, output ≤ 120 words plus one recommendation.
- **Memory extraction**: after each chat turn, `fastModel` scans the user's message for new preferences, dislikes, constraints, injuries and proposes `remember` calls that the UI shows as "Remembered: …" chips the user can undo.

### 6.5 Safety

A local keyword pre-filter (pain, hurt, injur, dizzy, faint, chest, numb, sharp) plus the `report_safety` tool. When safety state is active: engines hold (5.1 rule 1), the planner drops the affected pattern group, the system prompt instructs the coach to recommend professional advice and not to progress, and the UI shows a banner until the user resolves the event. The onboarding disclaimer states VigorEngine is not medical advice.

## 7. Apps

### 7.1 Information architecture (both apps)

Five top-level destinations, same on mobile tabs and web sidebar:

1. **Today** — readiness check-in card, today's plan (or "Ask for a workout"), nutrition ring with remaining macros, quick log, open insights, coach entry
2. **Train** — history calendar, workout detail, exercise library, per-exercise stats and PRs, session mode entry
3. **Eat** — day log by meal, saved meals, inventory, recipes, meal plans
4. **Progress** — strength charts (e1RM per exercise), body weight and measurements, photos compare, consistency, weekly reviews
5. **You** — profile, goals, equipment, targets, memories (view/edit/delete/forget), notifications, API key and models, export/import, safety events

The coach chat is reachable from every screen (floating button on mobile, right rail on web). **Session mode** is a full-screen flow: one exercise at a time, set rows with target vs last time, RPE picker, rest timer with notification, "can't do this" → substitution sheet, notes, finish summary with PRs.

### 7.2 State and data flow

- TanStack Query over repositories in both apps; query keys are defined once in `packages/core/queries` so invalidation rules are shared.
- Session mode keeps in-progress set entry in a Zustand store and flushes to `sets` on every confirmation so a crash loses nothing.
- View-model builders (`buildTodayView`, `buildExerciseStats`, `buildProgressSeries`) live in `packages/core` and are tested there; components only render.

### 7.3 Mobile specifics

Expo Router file routes. Rest timer uses `expo-notifications` local scheduling so it fires with the screen off. Photos stored in `FileSystem.documentDirectory/photos/` and referenced by relative path. Reminders are local notifications planned by `packages/core/reminders`: a workout reminder is skipped if a workout is already completed today, a meal-log reminder is skipped if a meal was logged in the last 3 hours, protein reminder fires only if remaining protein > 40 g after 18:00, weekly review on the user's chosen day.

### 7.4 Web specifics

Vite + React 19 + React Router. `vite-plugin-pwa` with a precache manifest so the shell loads offline. SQLite worker owns the OPFS handle; the main thread talks to it over a small RPC. Photos stored in OPFS. Web Notifications only when the tab is open; the settings page says so.

### 7.5 Design tokens

`packages/ui-tokens` exports one palette and type scale used by both apps. Directive for the UI agents: an athletic, unfussy look. Deep green-black grounds with a warm off-white text, a single accent in burnt amber for actions and PR moments, semantic green/amber/red reserved for readiness and target states. Typography: a condensed grotesk for headings and numbers, a humanist sans for body. Tabular numerals everywhere a number sits in a column.

## 8. Offline, privacy, export

- All data stays in the device SQLite file and app sandbox. The only outbound host is `api.anthropic.com`.
- The `ai_jobs` queue retries with backoff when the Network adapter reports online; jobs are idempotent by `id`.
- Export produces `vigorengine-YYYY-MM-DD.json` (all tables + photos as base64) encrypted with a passphrase (AES-GCM via WebCrypto on web and `expo-crypto` on mobile). Import validates schema version and offers merge or replace.
- Memory controls: every memory row is visible, editable and deletable in **You → Memories**. "Forget that" in chat calls `forget` and confirms.
- The API key is never logged, never included in exports, and can be removed with one tap.

## 10. Testing and quality bar

- `packages/core`: vitest unit tests for every engine with fixture histories, including the two examples from `idea.md` §5 (20 lb × 12/12/12 → increase; 25 lb × 8/6/6 → hold). Target ≥ 90 % line coverage in `core`.
- `packages/db`: repository tests against an in-memory `better-sqlite3` driver implementing `SqlDriver`; migrations tested from empty and from each prior version.
- `packages/ai`: tools tested with a fake driver; prompt assembly tested for cache-prefix stability (same inputs → byte-identical prefix); structured-output schemas round-trip tested. Live API tests are opt-in behind `VIGOR_LIVE_AI=1`.
- Apps: component tests for session mode and food log; Playwright smoke test for web (onboard → log workout → see PR); Maestro flow for mobile is optional in v1.
- CI script `pnpm check` runs typecheck, lint, tests across the workspace and must pass before any phase is called done.

## 11. Conventions for build agents

- TypeScript strict, ESM, `zod` for every boundary (tool inputs, structured outputs, import bundles, settings).
- Never store display units. Never compute progression in a component.
- Every engine output includes `rationale`. Every coach-visible recommendation surfaces it behind "Why?".
- No feature reads the API key outside `packages/ai/client.ts` and the settings screen.
- Load the `claude-api` skill before writing any Anthropic SDK code and follow its TypeScript README; verify with the `count_tokens` endpoint that the assembled coach context stays under 8k tokens on a full fixture.
- Commit per package with a message naming the phase and package. Do not skip hooks.
